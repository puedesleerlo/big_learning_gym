# Architecture and invariants

This is the descriptive source of truth for the implemented system. Read the accepted constraints in [`DECISIONS.md`](../DECISIONS.md) and the current behavioral contracts in [`ALGORITHMS.md`](ALGORITHMS.md). Update this file when implementation boundaries or data flows change; do not use a documentation edit as authorization to change a decision.

This is an event-driven modular monolith with shared transactional storage and independently built React frontends. The implementation is intentionally small enough to inspect and operate for one learner. It implements the two loops and authority boundaries in the supplied architecture; it does not claim every long-term connector, training method or research workflow is implemented.

## Authority and memory

`gym/store.py` separates the append-oriented evidence journal, versioned predictions and decisions. Current records are replaceable projections with identity scoped by record kind. Predictions retain input evidence, state revision, model version and invalidation dependencies. Schedule decisions retain inputs, rationale, alternatives, approval and execution state. Source versions, submission versions and rubric versions preserve historical interpretation.

A database transaction serializes a mutation with its evidence and outgoing job. SQLite uses `BEGIN IMMEDIATE`; PostgreSQL locks the singleton state row. No LLM output is authoritative about deadlines, instructor grades, calendar feasibility or a learner's psychological traits. Core operation does not depend on adaptation or a model provider being available.

## Module responsibilities

- `ingestion.py` preserves originals and extracts anchored text from PDFs, slide decks, documents, text, CSV and notebooks. Learner corrections create versions. Instructional content, assessment examples, rubrics, submissions and research sources have distinct roles.
- `assignments.py` handles reconstruction-confirmed style profiles, editable rubric proposals, rubric versions, assignment drafts, attachment snapshots, local submissions and separately attributed instructor outcomes. Review recommendations are scoped to the actual assignment.
- `generation.py` keeps a blueprint, source/profile/rubric snapshots, role provenance and independent verification. Up to 40 items are generated in batches of four; optional shared cases are created once and reused. Invalid or duplicate items are quarantined. A simulation cannot be partially published.
- `sessions.py` seals answer keys, records attempts and permitted aids, caps active-time heartbeats, tracks prior exposure and defers simulation feedback and learner updates until completion. Reopening an item does not erase evidence of prior assistance.
- `assessment.py` judges the submitted work against the frozen rubric. Every evidence quotation must exist in the submitted text. It excludes tutor conversation, confidence and predicted score from the assessor input. Open-response scores are provisional model judgments.
- `learning.py` maintains course-scoped, dimension-specific evidence summaries, delayed-check dates, revisable hypotheses and recommendations. Its weighted beta summaries are transparent heuristics, not calibrated mastery probabilities. Official grades remain scoped outcomes.
- `planning.py` owns scheduling. Remaining effort comes from the current completion criterion, not elapsed-time subtraction. The deterministic planner respects availability, commitments, deadlines, prerequisites, splitting, setup time, pins, workload and slack, with a ten-percent exploration budget. Failure to fit under its greedy policy is reported as a conflict; it is not a proof that no possible schedule exists.
- `calendar.py` treats fixed commitments, authoritative deadlines and app-owned study blocks differently. ICS identities, sequences, cancellations, recurring instances and date-only deadlines retain provenance. Missing entries in an import are not silent deletions.
- `adaptation.py` evaluates predicted effort and independent performance against later observed outcomes. Late arrival and target scope are checked. Effort candidates use point-in-time chronological validation, shadow status, explicit activation and rollback. Predictions made with different historical model multipliers are normalized before candidate fitting. An intervention ledger can record alternatives and assignment probabilities; causal effect estimation is not implemented.
- `worker.py` handles priorities, leases with renewal, bounded retries/backoff, idempotency and failed-job inspection. Schedule repairs debounce over 30-second windows. Daily planning and weekly deterministic evaluation catch up while the worker runs. These are application jobs, not desktop app automations.
- `llm.py` routes each role independently, bounds input/calls/retries, validates responses and records redacted provenance. OpenAI-compatible and native Anthropic transports are separate adapters. Providers cannot manipulate the calendar or execute learner code.
- `backup.py` produces a coherent portable snapshot and checksums referenced originals. Restore refuses a nonempty destination and recovers interrupted leases.
- `authoring.py` validates curriculum, guides, terms and authored items with provenance, revision checks and atomic imports. Item replacement preserves historical identities. Authoring produces content, not learner evidence.
- `lab_activity.py` owns named, versioned labs within a course. A course can have many labs; each lesson has a separate identity and references a course module. The catalog, validation, preview and publication routes use the same reference and revision checks. `lab_blocks.py` declares supported reading, prediction, worked-example, parameter-experiment, reflection, practice-assessment, coursework, media, visualization and discussion activities. The web catalog and authoring form use these contracts; MCP delegates to the same API.
- `lab_tutor.py` reserves idempotent discussion requests in shared storage, calls the existing `Router` tutor role outside a database transaction, then rechecks visit/simulation state and atomically records the attributed reply and assistance event. Pinned instructional source fragments and bounded recent conversation supply context; assessment keys, grades and unrelated history do not. The existing role config controls provider, model and call budget.
- Lab visits pin their lab version, lesson and sources. Reading, experiment inputs/results, saved predictions/reflections, active time and elapsed time are preparation evidence. Active time still uses server timestamps and a 45-second heartbeat cap. Only an unanswered session in the same course/module can link to a visit; exposures remain attributed assistance. Practice scoring and capability updates still belong to the existing session/assessment/learning services. Coursework references the existing assignment and rubric workflow; a click does not submit work or complete a task.
- `agent_api.py` exposes live capabilities, schemas and validated authoring routes through the existing API. `agent_client.py` is an HTTP client. Agent transport extensions must delegate to these workflows and must not introduce direct database writes or independent domain rules (D-009).

## Lab compatibility and extension

Lab identity is globally unique and its owning `course_id` cannot change. Existing records whose ID equals the course ID remain valid; old lesson IDs default to their module IDs, and old visits without explicit lab/lesson IDs resolve to their original course/module. No migration rewrites history or lab-version snapshots. New visits record explicit identities, so two labs sharing a module have distinct activity histories. Existing causal experiment widgets remain supported as a legacy presentation, while new generic activities are declarative blocks. Research-paper sections are optional.

`POST /api/labs/{lab_id}/validate` and `/preview` perform no writes. Publication revalidates the same body in a transaction and rejects stale revisions. Source versions must be confirmed instructional/research material from that course; coursework and its rubric must have compatible ownership. Lesson and lab prerequisite graphs are acyclic and guide sequencing; they do not automatically assert mastery or gate access. Assessment blocks use the existing question bank and report shortages during validation.

Parameter experiments compute only a bounded weighted sum (`offset + sum(coefficient * input)`). Server-recorded results are recomputed from the pinned configuration; a client cannot supply the output. A lesson supports one linked practice assessment per visit. Predictions/reflections remain ungraded observations and never become independent attempts by publication or preview.

Registry 2.0 adds parametric rich blocks under D-011. Media uses native HTTPS video/audio files or normalized YouTube privacy-domain/Vimeo embed URLs; no remote request occurs until the learner or preview author loads it. Transcripts are plain text; native captions use HTTPS WebVTT and may require CORS from the media host. Clip starts are supported throughout; end bounds use native player controls or YouTube's embed option. Vimeo end bounds are rejected. Pausing the visit unloads players. A load records exposure, never claimed playback duration or completion. This does not add media generation, a media-file upload/transcoding service, or a login bypass for institutional recordings.

Custom visualizations accept self-contained HTML, CSS, JavaScript, teaching data and bounded numeric controls. `packages/gym-frontend/visualization.js` (re-exported by the standard Gym) builds a trusted outer frame whose `frame-src about:` policy confines the untrusted inner frame; both use `sandbox="allow-scripts"` without same-origin, forms, popups, downloads or navigation privileges. Inner CSP blocks network subresources, fetch, workers and nested frames. Only data and selected control values enter the inner document. The application accepts no messages or outputs from it. Visualizations can be tried in preview without evidence; actual run actions validate controls against the pinned version and record preparation, not trusted computation results. No arbitrary code executes in Python or in the application document. This browser sandbox is not a CPU/memory quota; dependencies must be bundled, and authored visualizations still require functional review. Browser policy reference: [MDN iframe sandbox](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe#sandbox).

Discussion blocks configure prompt, objectives, style, turn limit and target response length. `/api/lab-activities/{id}/discussion` requires an active running visit, expected turn and idempotency key. Replies cite only supplied fragment IDs and retain source snippets and model provenance. A failed response creates no successful turn or assistance event; a successful reply increments the existing help counter. Client retries do not repeat completed calls. Pending calls exclude competing turns, expire after one hour for crash recovery, and are checked again before publishing a reply. Provider execution after a crash cannot be guaranteed exactly once. Source content is untrusted; source membership checks do not prove model factual correctness. Tutor exchanges never award grades or mastery and do not enter assessor inputs. Publication/preview makes no model calls, and ordinary labs remain usable without a configured model.

## Unified authoring and profile evolution (D-013)

The same course owns sources, actual coursework, teaching labs, targeted profiles and generation runs. Uploads add evidence to the material library; `/api/assignments` creates the separate obligation and source links. Coursework `purpose=self_study` holds optional exercises referenced by teaching labs without creating scheduling duties. Missing rubrics are nullable and visibly unknown; assessable local submissions still require an explicit pinned rubric. Assignment revisions preserve historical submission snapshots and use Planning to synchronize remaining obligations.

Profiles have an explicit `target` and optional `target_assignment_id` for intended future coursework. `assignment_ids` are prior coursework examples, `source_ids` prior assessment/rubric sources, `material_source_ids` prior instruction, and `emergent_source_ids` newly available instruction/assessment/rubric evidence. Sources must be confirmed and same-course; submissions and feedback are ineligible. Selected coursework and rubric snapshots, prior material fragments, emergent fragments and a derived practice rubric are stored separately. Retrieved context remains a bounded lexical subset, not exhaustive document comprehension. Profile generation and manual author proposals require review before generation uses them.

`POST /api/profiles/{id}/rerun` uses a revision check and exact-payload idempotency receipt, refreshes selected inputs and increments `run_version`. Creation, proposals, confirmation and failures save immutable `assessment_profile_version` records, available through `GET /api/profiles/{id}/versions`. Jobs carry the run number so superseded work cannot publish into a newer run. New evidence alone does not replace the current profile. Reruns make configured model calls and may need correction; provider execution across a process crash is not guaranteed exactly once.

Generation pins an explicit confirmed profile revision (optionally `profile_version_id`) and instructional fragment snapshots before enqueueing. Counterfactual allocation fits within the chosen item formats and total. Private item metadata describes changed assumptions, source-supported reasoning and uncertainty; a separate verification result must explicitly accept the derivation. Session public-item allowlists exclude it. `POST /api/generations/{id}/rerun` creates a linked new blueprint using the latest confirmed profile or a selected confirmed historical version, retaining old items and attempts. Sessions may specify `blueprint_id` to practice a particular generated set. Ordinary practice samples both practice and legacy transfer pools; legacy focused transfer mode is retained. Both share existing evidence/scoring services.

`POST /api/assignments/{id}/outcomes` stores `coursework_outcome` independently of local submissions or model assessments. Outcomes may be feedback-only; they retain actual score/max points, attribution, source reference, observation time, nullable original occurrence time, separate learner comments, limitations and supersession. Exact retries return one result. Explicit historical completion closes the linked task through Planning with no fabricated effort; schedules are not accepted or rewritten. These unlinked outcomes do not enter the existing submission-based recommendation or general capability algorithms. An original feedback artifact version can be snapshotted and its current projection explicitly reclassified to coursework. Original artifacts/reviews remain stored, while research authoring/critique rejects the reclassified record.

The standard UI exposes material, prior/emergent evidence, future intent, profile history/reruns and practice regeneration under Authoring; actual outcomes live in Coursework. The existing REST schema and agent capabilities describe the typed inputs; generic MCP reads/requests delegate without independent persistence. `skills/learning-gym` documents the prepared-agent workflow. Independent frontends continue to use shared workflows or link to the standard UI. Historical profiles and unprofiled API generation retain compatibility; neither is represented as newly validated targeted assessment.

Completed coursework presents saved instructor grades and feedback first. The optional assignment-document picker describes the original requirements and excludes feedback and learner-submission files; original instructions/rubrics and the learner-work editor are collapsed separately for completed tasks. Feedback files upload through the existing sources route with `role=feedback` and attach to the outcome's `source_id`; the UI can read their preserved extracted text. Uploading alone does not infer a score or create a submission. Corrections retain attachment and import provenance in a superseding outcome, with earlier records available as collapsed history. No new persistence or grading authority is introduced.

## Experience adaptation and local workspaces (D-012)

The domain application stays shared. `gym/workspaces.py` loads optional local JSON configuration; `gym/cli.py --workspace FILE serve` selects the database, original-file directory and localhost port. An independently launched worker reads the same configuration. Each process has one Store and the existing evidence, outbox, planner and assessment services. Without configuration, the previous default store and launch behavior remain unchanged. Named workspaces require explicit directories; use distinct database URLs, directories, identities and ports for different companies. These configurations are not a hosted tenancy or permission model.

`gym/frontends.py` validates installed manifests and serves only their `dist/` builds at `/experience/<id>/`. Unknown experiences and missing assets return 404; extensionless frontend routes receive that build's index. `/app-config.json` exposes only workspace identity, contract version, API base and installed experience metadata. It exposes no filesystem paths or credentials. API authentication, host and origin validation still apply. The standard Gym remains `/` and supports explicit query deep links for labs, sessions, coursework and the other existing modules.

`packages/gym-frontend/` supplies the styling-free client, TypeScript declarations, React hooks, namespaced session storage and reusable rich activities. It serializes clocks and supported mutations, retains idempotency receipts across interrupted requests, and pauses visits before linked practice. Session creation has no idempotency key in the existing API: an uncertain response leaves a recoverable marker and requires selecting a matching recent session, never automatic recreation. The recovery list uses the existing overview's recent-session window; the full Gym remains available to inspect older work. Pending link operations retain the known session ID. Preview uses an explicitly selected in-memory synthetic transport and has no network fallback. Application exits attempt a keepalive pause; abrupt process/network loss still relies on the backend's 45-second tick cap.

The standard Gym uses the shared client for linked-practice creation/recovery and answer receipts, and uses the same workspace namespace for credentials, drafts and session references, with legacy-key migration only in the default workspace. Per-question answer drafts are shared between presentations and no longer reset through a delayed question-change effect. Company frontend changes cannot duplicate evidence because all durable reads/writes go through the same API. Rich media and visualization functions moved into the integration kit without changing D-011 isolation. Company CSS styles their public markup; authored visualization scripts still execute only inside nested opaque sandbox frames.

`adaptations/makitra/` is an independent React/Vite build using the actual pinned `@makitra/react` archive and bundled fonts. It owns layout, navigation, components and colors. It implements the activity registry's eleven types, all six question formats, linked practice/transfer, assistance and backend-visible feedback. It links legacy presentations, coursework and other modules to the standard Gym. Design-system packages are absent from the platform and shared kit. The archive's provenance and personal non-commercial limitation are recorded beside it.

`gym/frontend_contracts.py` enriches OpenAPI documentation without filtering runtime responses or changing route payloads. `gym/frontend_kit.py` exports a self-contained client, minimal starter, progressive skill, activity registry, OpenAPI snapshot and synthetic examples from a temporary application/store. It never opens the configured learner database for contract generation. The starter deliberately leaves some activity presentation to the generating agent; use its journey references and verification scenarios to complete a company frontend. Exporting is not authoring curriculum or creating learner history.

Run instructions and configuration examples are in [`EXPERIENCES.md`](EXPERIENCES.md). Installed frontend JavaScript is trusted application code with the same workspace access as the standard UI. Package manifests and compatibility checks detect selected integration errors; they are not a sandbox or automatic security certification. Company content still uses existing document/content imports; live synchronization, hosted multi-user access and kitchen application logic are outside this experiment.

## Change control

`AGENTS.md` and the always-applied Cursor rule instruct coding agents to read the decision register and this architecture before edits. `docs/ALGORITHMS.md` records formulas, cutoffs, versions and validation expectations. Protected changes require a path-specific record under `docs/changes/`; the architecture checker and behavioral tests detect selected boundary violations and unrecorded changes. These are repository controls, not a substitute for independent review.

The CI workflow runs the checker, backend tests on SQLite/PostgreSQL, all frontend builds, shared client tests and disposable browser journeys using pnpm. GitHub enforcement is separate: required checks, owner review, protected `main`, and limited agent credentials must be configured by the maintainer. See [`CHANGE_CONTROL.md`](CHANGE_CONTROL.md) for the activation procedure and its limits. Adding these files does not itself enable GitHub protection.

## Operational sequence

An attempt or source/task/calendar change enters a transaction. Evidence is appended, relevant projections change, state advances and a job is committed. The worker invalidates dependent estimates and proposes repair. The learner reviews and accepts an applicable schedule proposal. Replaying the same idempotency key has one stored effect.

The adaptation process runs independently: select eligible prediction/outcome pairs, enforce timestamp and scope validity, fit on past evidence, test against later observations, retain the baseline when evidence is insufficient, and save a candidate in shadow only when the gates pass. Activation never rewrites historical forecasts.

## Extension boundaries and current limits

Calendar connectors currently use manual entries and ICS snapshots/import/export; there is no OAuth or live bidirectional calendar sync. Scanned PDFs, complex diagrams and damaged equations need learner correction: no OCR or vision extraction is included. Retrieval uses anchored lexical ranking, not an embedding service, and uses a bounded subset of long source packs.

The coding workbench stores code and notebook output; it does not execute arbitrary code. Research critique does not verify cited papers externally. Learner-state parameters use a transparent baseline; no deep knowledge tracing, reinforcement learning or causal personalization claims are made. Shared-case questions use a fixed trailing section; precise section arrangements and nuanced stylistic constraints require review. Simulation answers are committed individually and cannot yet be edited after saving; completion seals the assessment and releases feedback.

This is a local, single-user release. Public multi-user deployment, tenant isolation, automated encrypted backups and institutional submission integrations need additional work. Token authentication, same-origin mutation checks and trusted host validation are included, but the application should remain bound to localhost in this configuration.
